Задача

Диалог течёт естественно: начался про «Состояние» — ушёл в «Реализацию». Сейчас весь текст падает в формальный раздел (messages.sphere_id), где физически идёт разговор. Смысл оседает не там → данные грязные.

Нужно: агент в фоне разбирает поток на смысловые фрагменты и относит каждый в ту сферу, о которой он по сути — не мешая течению диалога. Чтобы данные упорядочивались по смыслу.

1. ЧТО ИЗВЛЕКАЕМ — единицы смысла (из реплик ЮЗЕРА)

Работа на уровне фрагмента, не реплики целиком. Одна реплика = 1–4 единицы.

Тип (slug) Что это В промпт сцены / модель
tsennost устойчивый принцип, по которому человек оценивает Ориентиры — отбор «своих» деталей сцены
zhelanie конкретное намерение / образ желаемого Вектор — сюжет сцены
sostoyanie_tek как чувствует себя сейчас контекст восприятия
sostoyanie_zhel как хочет себя чувствовать эмоциональный тон сцены
fakt обстоятельство жизни (кто/где/с кем) реализм, узнаваемость
obraz метафора / визуальный образ (беречь дословно) прямой материал генерации
napryazhenie конфликт / боль / сопротивление точка разрешения в сцене
resurs на что опирается (сила, навык, поддержка) элементы опоры в сцене

4-слойная модель личности (куда копятся единицы)

Слой 1 КОНТЕКСТ   ← fakt                         (медленный, реализм)
Слой 2 СОСТОЯНИЯ  ← sostoyanie_tek/_zhel         (динамичный, тон сцены)
Слой 3 ОРИЕНТИРЫ  ← tsennost, resurs             (накопительный, «своё»)
Слой 4 ВЕКТОР     ← zhelanie, napryazhenie, obraz (живой, Life Vector + сюжет)

Что НЕ извлекать

Вежливость («ок/спасибо»), реакции на бота («интересный вопрос»), мета-вопросы, «не знаю» без содержания, слишком общее («хочу всего побольше»), чужие слова («мама говорила…» → метка «чужой голос», не в модель). Повтор уже извлечённого → поднять confidence, не плодить дубль.

2. МУЛЬТИ-ЛЕЙБЛ + лестница разрешения

  • Одна единица → 1 сфера primary, максимум 2 (primary+secondary). Три = фрагмент не разбит.
  • secondary ставить только если у обеих сфер уверенность ≥ medium. low-secondary не ставим.
  • primary = где субъект желания/действия; secondary = контекст/причина.
  • Пример: «хочу запустить дело, чтобы наконец чувствовать себя живым» → primary realizatsiya + secondary sostoyanie.

Лестница, когда тянет в две сферы: 1. Адресат желания: внутрь себя → Состояние/Знание · к одному → Любовь · к родне/дому → Дом · к кругу → Окружение · к миру/публике → Проявленность/Реализация. 2. Природа денег/благ: опора и достаток → Ресурсы · рычаг независимости → Свобода · мерило дела → Реализация. 3. Стадия дела: создать/начать → Творчество · достичь/повлиять/след → Реализация. 4. Чувство vs процесс: ясность-как-ощущение → Состояние · понимание-как-путь → Знание. 5. 50/50 → клади в сферу, названную словом человека, не выводи логически. («спокойствие за будущее» = Ресурсы по слову «будущее», хотя «спокойствие» звучит как Состояние.)

Самые частые ошибки классификатора (собрать тест из 10–15 реальных фраз ДО доверия разметке): пары sostoyanie ↔ resursy и sostoyanie ↔ svoboda.

3. ТАКСОНОМИЯ МАРКЕРОВ (ядро + как отличать соседей)

Полная версия с маркерами по каждой сфере и всеми границами — в этом же файле ниже (раздел «Приложение А»). Принцип классификатора: спрашивай не «про что слова», а «про какой запрос человека». Деньги могут быть про Ресурсы, Свободу или Реализацию — зависит от того, что человек хочет.

Ключевые разводки соседей: - Состояние vs Свобода: покой внутри vs покой от внешних условий. Убрать обстоятельства — желание осталось? → Состояние. - Ресурсы vs Свобода: «иметь и не бояться» → Ресурсы · «мочь и не зависеть» → Свобода. - Реализация vs Творчество: создать/процесс → Творчество · влияние/след/признание → Реализация. - Дом vs Любовь: множество и корни → Дом · двое и близость → Любовь. - Состояние vs Знание: ясность-чувство → Состояние · понимание-путь → Знание. - Реализация vs Проявленность: «что я меняю» → Реализация · «каким меня видят» → Проявленность.

4. ПРОМПТ КЛАССИФИКАТОРА (готов к вставке)

Ты — аналитик диалогов Elyne. Разбери сообщения ПОЛЬЗОВАТЕЛЯ на смысловые
единицы и отнеси каждую к сфере жизни ПО СМЫСЛУ (не по разделу разговора).

# Сферы (строго эти id):
sostoyanie | resursy | realizatsiya | dom_semya | lyubov |
tvorchestvo | znanie | svoboda | okruzhenie | proyavlennost

# Типы единиц:
tsennost | zhelanie | sostoyanie_tek | sostoyanie_zhel |
fakt | obraz | napryazhenie | resurs

# Правила:
- Уровень ФРАГМЕНТА, не реплики. Одна реплика = 1–4 единицы.
- Одна единица → 1 сфера (primary), максимум 2 (primary+secondary).
  secondary только если у обеих уверенность ≥ medium.
- Пропускай шум: вежливость, реакции на бота, мета-вопросы, «не знаю» без сути.
- Уважай слово человека: клади в сферу из его формулировки, не переумничивай.
- При споре: адресат желания → природа денег → стадия дела →
  чувство vs процесс → слово человека.
- excerpt: дословно или сжатие ≤120 символов. obraz беречь дословно.
- confidence: high (названо прямо) | medium (устойчивый вывод) | low (косвенно).

Верни ТОЛЬКО JSON-массив, без текста вокруг. Ничего значимого → [].
Элемент:
{"assigned_sphere": "...", "secondary_sphere": "..."|null,
 "unit_type": "...", "excerpt": "...", "confidence": "high|medium|low"}

Сфера диалога (формальная): {formal_sphere}
Сообщения пользователя:
{messages_block}

confidence → число при записи: high=0.9, medium=0.6, low=0.3. Порог хранения ≥0.4 (low отсекается).

5. АРХИТЕКТУРА ФОНОВОГО ПАЙПЛАЙНА

Таблицы (расширяют, не ломают существующие)

CREATE TABLE IF NOT EXISTS semantic_insights (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    tg_user_id INTEGER NOT NULL,
    source_message_id INTEGER NOT NULL REFERENCES messages(id),
    formal_sphere TEXT NOT NULL,      -- где шёл диалог
    assigned_sphere TEXT NOT NULL,    -- по смыслу
    secondary_sphere TEXT,
    unit_type TEXT NOT NULL,
    excerpt TEXT NOT NULL,
    confidence REAL NOT NULL,         -- 0.0–1.0, порог ≥0.4
    model_version TEXT,
    created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_si_user_assigned ON semantic_insights(tg_user_id, assigned_sphere);
CREATE INDEX IF NOT EXISTS idx_si_source_msg ON semantic_insights(source_message_id);

CREATE TABLE IF NOT EXISTS semantic_sphere_profiles (
    tg_user_id INTEGER NOT NULL,
    sphere_id TEXT NOT NULL,          -- смысловая сфера
    summary TEXT, insight_count INTEGER DEFAULT 0,
    last_insight_at TEXT, updated_at TEXT,
    PRIMARY KEY (tg_user_id, sphere_id)
);

CREATE TABLE IF NOT EXISTS classification_log (   -- идемпотентность
    message_id INTEGER PRIMARY KEY REFERENCES messages(id),
    status TEXT NOT NULL,             -- pending|done|failed|skipped
    attempts INTEGER DEFAULT 0, error TEXT, processed_at TEXT
);

Триггер

Батч по 3–5 необработанных реплик юзера, в фоне (asyncio.Queue + один воркер), не блокируя ответ. Дозапуск, если прошло >10 мин с последней необработанной реплики (чтобы не терять концы брошенного диалога). Перед работой смотрим classification_log — done не трогаем (нет дублей при рестарте).

Модель

claude-haiku-4-5 через тот же claude -p (Max-подписка → классификация по сути бесплатна; один воркер = без параллельных вызовов → не упираемся в rate limit). Retry ×3 с backoff, JSON вырезаем регуляркой даже если модель добавила текст. Падение → пропуск, не роняем поток.

Агрегация в профиль

Инсайты по assigned_sphere (смысловой!) группируем по типу → краткая сводка в semantic_sphere_profiles. Старая sphere_profiles (формальный путь) остаётся — дашборд показывает оба слоя.

Дашборд /chats — cross_sphere_leaks

Запрос WHERE formal_sphere != assigned_sphere GROUP BY formal_sphere, assigned_sphere показывает куда и сколько раз утекает разговор — это прямой ответ на запрос Сергея, видно глазами в админке.

Точки интеграции

  • api/main.py: 3 таблицы в init_db(), глобальная classify_queue, classify_messages_batch() + process_pending_messages(), запуск воркера в startup(), 1 строка queue.put(...) после записи сообщения, эндпоинт /user/{id}/profile.
  • bot.py: не трогаем (классификация живёт в FastAPI, где хранятся messages).
  • Существующие таблицы: не изменяются.

Стоимость

~$0.002 на диалог из 25 реплик (Haiku). На Max через CLI — фактически в подписке. 100 юзеров/день ≈ $6/мес при прямом API.

6. РИСКИ / ПЛАН ПРОВЕРКИ

  1. ID сфер (раздел 0) — финал с Олегом ДО внедрения.
  2. Тест классификатора — 10–15 реальных фраз из elyne.db на парах Состояние↔Ресурсы и Состояние↔Свобода, сверить разметку вручную до доверия.
  3. Привязка insight→конкретный message_id: в MVP вешаем на первое сообщение батча; для точности — попросить модель возвращать source_msg_id (расширить промпт).
  4. Очередь: maxsize=50 + лог переполнения; при массовом онбординге — второй воркер.
