2. Profile Summary Pipeline

2.1 Что должно быть

GP ID=15 — profile_summary_system генерирует Character Profile:

Character Profile:

Gender: male / female
Age Context: [25-35 / 30-45 / ...]
Archetype: [Creative Explorer / Global Leader / Quiet Achiever / ...]
Core Motives: [recognition, freedom, connection, ...]
Expression Model: [through visual impact / through movement / ...]
Visual Identity: [ranked style slugs, e.g. Casual > Boho > Old Money]
Social Signal: [first impression the user wants to create]
Life Level: [calm / growth / new opportunities / high level / influence]
Environment Type: [city / sea / nature / nomadic / ...]
Realization Path: [self-expression / entrepreneurship / creativity / ...]
Realization Domain: [business / arts / personal projects / ...]
Energy Type: [expansive / contemplative / expressive / ...]
Key Answer Locks:
  - [якорь 1, обязан проявиться в каждой сцене]
  - [якорь 2]
  - [якорь 3]

Key Answer Locks — это жёсткие ограничения: если хотя бы 3 не проявились в сцене → сцена невалидна (по логике промта, но нет внешнего валидатора — баг).

2.2 Что реально происходит для monad@elyne.online

Поле Ожидание Реальность
profile_summary Character Profile (~300-500 слов) ERROR STRING («Отсутствуют входные данные…»)
Key Answer Locks 3 конкретных якоря ОТСУТСТВУЮТ
Archetype «Creative Explorer» или аналог ОТСУТСТВУЕТ
Visual Identity Ranked style slugs ОТСУТСТВУЕТ
Gender lock male / female определяется через onboarding_answers косвенно

Почему это произошло:
Промт profile_summary_system требует структурированных ответов Q1-Q18. У monad@elyne.online анкета либо не была завершена в стандартном формате, либо ответы пришли в нестандартном виде. LLM получил недостаточный контекст → вернул отказ «нет входных данных» вместо профиля.

2.3 Как profile_summary передаётся дальше

После сохранения в БД profile_summary подаётся дословно в каждый field_scene meta_prompt:

Профиль пользователя = Отсутствуют входные данные от пользователя 
(ответы, предпочтения, выборы стилей), необходимые для формирования 
профиля личности, определения Key Answer Locks и интерпретации 
визуальной идентичности согласно заданным ограничениям 
(No Synthetic Personality)...

Это текст-ошибка в самом центре генерации сцены. LLM для sphere_scene читает не «кто этот человек», а «данные отсутствуют». Он продолжает генерацию, опираясь исключительно на onboarding_answers и sphere meta_prompt.

         Materials

3.2 Style block в FAL prompt (пример для Casual)

Стиль передаётся как ДОПОЛНИТЕЛЬНЫЙ БЛОК В ХВОСТЕ FAL-промта. Он не интегрируется в reasoning сцены — добавляется после --- разделителя:

[detailed_description от scene_system]

---

[image_instructions technical block]

---

Стиль одежды: Visual Code: современная расслабленность... Base Wardrobe: 
плотная футболка, свободный свитшот, рубашка... Color Logic: молочный, 
серый, чёрный, navy... Avoid: старый свитер и чиносы...

Проблема: FAL читает prompt как линейный текст. Хвост имеет меньший вес, чем начало. detailed_description генерируется LLM (150-300 слов) и доминирует над style block (~50 слов). Стиль одежды фактически становится suggestion, а не constraint.

3.3 Где определяется dominant style / secondary styles

Сейчас: только через profile_summary.visual_identity_ranked, но это поле = error.
Фактически: стиль берётся из Q7-Q12 (binary выборы при онбординге) напрямую, без ранжирования.
Смешение стилей: не реализовано. Система берёт первый стиль и применяет его как единственный.

3.4 Style adaptation rules (sphere-context)

В Style Profiles v4 (Часть 3) прописана применимость каждого стиля по сферам, но эта матрица находится в vault-документе, а не в промте. В production промте: - fallback на Casual/Old Money описан в архитектуре, но не автоматизирован в pipeline - incompatibility check (Sport Casual в Партнёрстве = провал) не проверяется автоматически - negative_prompt из Части 4 не прокидывается в FAL negative_prompt

5. Style Drift Analysis

5.1 Где происходит identity drift

Точка 1: Profile_summary → scene_system
Если profile_summary = error, LLM не знает кто перед ним. Он «синтезирует личность» из onboarding_answers — что прямо запрещено принципом No.Synthetic.Personality. Результат: каждая генерация синтезирует РАЗНУЮ личность из тех же ответов → drift между сценами.

Точка 2: Style block position в FAL prompt
Style block идёт в хвосте. FAL сначала строит сцену по detailed_description (200+ слов), потом видит style block (50 слов). Одежда генерируется «в духе», а не точно. Два запуска одного профиля = разный крой, цвет, силуэт.

Точка 3: No previous_scenes continuity
Архитектурная дыра: clothing/visual/emotional continuity между сценами не передаётся. При генерации Сферы 9 система не знает что было в Сфере 1. Человек выглядит по-разному в каждой сфере.

Точка 4: Style fallback без уведомления
Если выбранный стиль не покрывает сферу (матрица v4, часть 3), система применяет fallback на Casual/Old Money. Пользователь не видит этого. Он видит образ, который не совпадает с тем что выбрал.

5.2 Где style drift

Причина Механизм Эффект
Style block в хвосте FAL prompt Малый вес инструкции для FAL Другой силуэт / оттенок в каждом кадре
Нет visual_identity_ranked Стиль берётся из Q7-Q12 без ранжирования Непоследовательный выбор при multi-style
Нет negative_prompt Запреты из style-profiles v4 не применяются в FAL Генерирует запрещённые детали
Несовместимые стили не блокируются Нет automatch sphere × style Sport Casual в Партнёрстве
Нет cross-sphere continuity Каждая сцена — отдельный запрос Пальто в Сфере 1, джинсы в Сфере 9

5.3 Где sphere overrides user

Sphere Behavioral Profile (добавлен 15.05) задаёт: - Life Pacing: медленный / живой / лёгкий - Relational Density: Low / Medium / High - Scene Types: restoration / belonging / movement - Cliché Risks (то, что система ПЫТАЕТСЯ избегать)

Когда profile = error, sphere meta-prompt становится единственным источником истины. LLM читает «Окружение» → Relational Density = HIGH, people required → строит сцену вокруг социального взаимодействия. Даже если юзер написал «хочу сцену где я один исследую город».

6. Scene Interpretation Collapse

6.1 Кейс: ответы → ресторан

Исходные сигналы пользователя:

Приоритеты: свобода, движение, масштаб
Среда: разные страны
Способ проявления: влияние на других, осознанность, свобода и движение
Уровень: на широком уровне с большим влиянием
Sphere_q3 (фантом): «новые улицы, новые страны, исследование»

Ожидаемая сцена: человек в движении, новые пространства, одиночество в открытом мире, исследование.

Результат: ресторан, вино, глобальный интеллектуальный круг, social belonging.

6.2 На каком этапе pipeline произошло схлопывание

Этап 1: Выбор сферы
Пользователь выбрал либо «Окружение» либо «Реализация». Обе сферы имеют высокую Relational Density. Sphere meta-prompt для Окружения: «люди обязательны, без них сфера не раскрывается».

Этап 2: 3-angle structure
Sphere meta-prompt требует три окна: - внутреннее (тихое, наедине) - взаимодействие/признание - действие/движение

Второй angle «взаимодействие/признание» → LLM интерпретирует «Быть признанным и увиденным» + «глобальный уровень» + «разные страны» → ресторан в иностранном городе с умными людьми. Это самый частотный safe archetype для «признание + международный + высокий уровень» в training data LLM.

Этап 3: Profile = error → нет якорей
Если бы Key Answer Locks работали, они могли бы зафиксировать: «исследование, движение, новые пространства — обязательны в каждой сцене». Без Key Answer Locks LLM свободен выбрать «ресторан» как валидное пространство для признания.

Этап 4: Prompt-block для «recognition» angle
Sphere meta-prompt для «Окружение» содержит фразы типа: - «встреча, разговор, включение в круг» - «принадлежность — это мои люди, это моя среда» - Narrative Behavior = «social_presence»

Это принудительный аттрактор. LLM видит задачу «сделай сцену для recognition» + «sphere = belonging/circle» → ресторан.

Этап 5: Emotional amplification усиливает
image_instructions добавляет «emotional atmosphere», «warmth», «vitality». Ресторан — эмотивно тёплая, понятная, «жизненная» локация. FAL рендерит с дополнительным эмоциональным amplification → ещё более уютный, притягательный ресторан.

Схлопывание происходит на шагах 2-3: выбор sphere + angle + broken profile identity.
Это не ошибка промта сферы — это отсутствие identity anchor, который должен был сказать «стоп, этот человек про движение, не про статику».

7. Narrative Engine Collapse

7.1 Почему сцены похожи

Оператор-vocabulary collapse (из explore-audit 17.05):
Из 8 реальных кадров пользователя oleg@elyne.online: - 8/8 — eye level - 7/8 — герой по центру - 6/8 — medium / medium wide - 0/8 — POV / OTS / extreme wide / low angle / silhouette

Система генерирует один camera grammar: eye-level centered medium portrait. Это lookbook-вокабуляр (Zara, Massimo Dutti), не кино. Кино требует 4-5 разных camera grammars за эпизод.

Почему это происходит:
detailed_description генерируется LLM, который не получает camera grammar instructions. Формат: «человек стоит / идёт / сидит, свет [описание], одежда [описание], эмоция [описание]». Это prose description, не cinematographer brief. FAL интерпретирует prose → eye-level centered portrait.

7.2 Concept-capsule vs point-in-time

Текущая базовая единица: смысловая капсула сферы
scene_title = «Точка перехода: Движение как жизнь»

У капсулы нет «потом». LLM при explore читает «надо создать ещё одну интерпретацию движения» → параллельная вариация, не следующий момент.

Нужная базовая единица: точка в пространстве-времени
scene_state = {location: «Лиссабон, терминал T1», time: «30 мин после посадки», action: «выход в город», context: «первый день нового маршрута»}

С scene_state у героя есть «потом» → следующий кадр = через 30 минут, уже на улице. Explore становится нарративом, а не вариацией.

7.3 Почему не работает «desire vector»

Сцены не создают «Хочу идти дальше» потому что:

  1. Нет narrative goal — у сцены нет destination (куда движется жизнь). Есть состояние (recognition / freedom / movement), но нет вектора (к чему идём).

  2. Anti-scripted-movie блок глушит события — промт explore явно запрещает «scripted movie feel». В итоге любое событие (встреча, открытие, прибытие) избегается → только атмосфера без нарративного напряжения.

  3. Centered composition = no off-frame tension — герой по центру, взгляд в камеру (или вперёд). Нет ничего за кадром, к чему тянет взгляд. Кино создаёт tension через off-frame элементы, POV shots, что-то что происходит ЗА героем.

  4. Safe cinematic behavior — FAL обучен на «правильных» lifestyle-фото. При неточных camera instructions генерирует наиболее статистически частую «красивую жизнь»: светлое пространство, человек с хорошим светом, нейтральный фон. Stock aesthetic.

8. Architectural Fixes

Fix 1: CRITICAL — Profile Summary Recovery

Проблема: profile_summary = error string → вся персонализация сломана.
Fix A (быстрый): Admin action для пересоздания profile_summary по уже имеющимся onboarding_answers. Денис делает admin-button «Recalculate Profile».
Fix B (архитектурный): Fallback-логика в pipeline: если profile_summary содержит «Отсутствуют» или пустой → trigger regeneration перед первой генерацией сцены.
Тест успеха: profile_summary содержит корректный Character Profile с Key Answer Locks для monad@elyne.online.

Fix 2: CRITICAL — Key Answer Locks validation

Проблема: Key Answer Locks прописаны в промте, но нет внешнего валидатора.
Fix: После генерации detailed_description — LLM-проверка: «присутствуют ли Key Answer Locks в тексте сцены? Если нет → regenerate».
Сложность: требует Дениса (retry logic в pipeline).
Минимальный вариант: добавить в scene_system prompt явный DEBUG CHECK с выводом в logs.

Fix 3: HIGH — Style block position → интеграция

Проблема: style block в хвосте FAL prompt имеет малый вес.
Fix: Перенести style description в НАЧАЛО detailed_description generation. То есть LLM при генерации сцены должен сначала определить как человек одет (из style slug), потом описать сцену вокруг этого.

Старый порядок: [scene description 200 слов] + [style block 50 слов]
Новый порядок:  [identity anchor] + [style specification] + [scene description]

Prompt-level fix: в scene_system добавить секцию «Шаг 0 — зафиксируй одежду»:

Перед описанием сцены определи:
- Какой элемент Base Wardrobe соответствует этому моменту (indoor/outdoor, публичный/приватный)?
- Какой цвет из Color Logic?
- Какой элемент из Avoid категорически исключён?
Затем опиши сцену с уже встроенным описанием одежды.

Fix 4: HIGH — Scene Interpretation Collapse: identity gate

Проблема: sphere meta-prompt override identity при broken profile.
Fix: Добавить IDENTITY GATE перед scene generation:

IDENTITY GATE (10-15 строк, вставляется первым в user-часть промта):
Этот пользователь → [3 Key Answer Locks из profile_summary]
Каждая сцена ОБЯЗАНА содержать хотя бы 2 из 3.
Если sphere предлагает сцену без этих элементов → искать другой archetype.

Для monad@elyne.online, если восстановить profile: Key Answer Locks могли бы быть: - «движение и новые пространства» - «признание через влияние, не через статику» - «исследование и осознанность»

С этими locks restaurant-сцена невалидна: статичный ресторан ≠ «движение».

Fix 5: HIGH — Narrative: scene_state как persistent artifact

Проблема: scene_title — смысловая капсула без «потом».
Fix: Добавить поле scene_state в generations table:

{
  "location": "Лиссабон, пешеходная улица Байру-Алту",
  "time_of_day": "поздний вечер",
  "weather": "тёплый ветер с реки",
  "action": "идёт без расписания, впервые в этом районе",
  "social_context": "один, никуда не спешит",
  "narrative_thread": "первый день нового маршрута",
  "what_comes_next": "найти место поужинать или просто пройти дальше"
}

Этот JSON передаётся в explore prompt как current_scene_state — и explore знает откуда генерировать следующий момент.
Требует Дениса: schema migration + first_scene generator returns scene_state JSON.

Fix 6: MEDIUM — Camera grammar vocabulary

Проблема: все 8 кадров = eye-level centered portrait.
Fix: Добавить в scene_system CAMERA BRIEF как отдельное JSON поле:

{
  "camera_grammar": "OTS",
  "shot_size": "medium wide",
  "angle": "slightly low",
  "hero_position": "left third",
  "depth": "foreground bokeh, hero mid, background scene",
  "movement_hint": "slight camera lean forward"
}

Это поле передаётся в FAL prompt в самом начале как жёсткая инструкция, не как prose. FAL лучше следует структурированным camera specs, чем prose описаниям.

6 обязательных грамматик для rotation (использовать в первых 3 сценах): 1. OTS (over-the-shoulder) — человек в движении, среда впереди 2. Крупный план фрагмента (руки, предмет, деталь окружения) 3. Full shot снизу (low angle, земля/асфальт, небо или открытое пространство вверху) 4. Силуэт contre-jour (контровой, человек не в центре, смещён) 5. POV walking — субъективная камера, hero вне кадра 6. Medium (стандартный) — только 1 из 6

Fix 7: MEDIUM — Recognition angle → movement fallback

Проблема: «взаимодействие/признание» angle = ресторан для любого профиля.
Fix: Добавить в sphere meta-prompt для каждого angle условный routing:

Угол «признание/контакт» — как строить:
- Если user_environment = «разные страны» / «движение» →
  признание через действие в пространстве (лекция в другом городе, разговор в transit, 
  случайное единение в публичном месте)
- Если user_realization = «влияние через создание» →
  признание через работу (показ, открытие, backstage)
- Если user_priority = «близость» →
  признание через отношения (партнёр, камерный ужин)
НЕ: дефолтный ресторан-wine-интеллектуальный круг для всех.

Fix 8: MEDIUM — Narrative goal + desire vector

Проблема: сцены illustrate state, не generate desire.
Fix: Добавить в scene_system обязательное поле narrative_promise:

narrative_promise: «что происходит через 10 минут, что заставляет хотеть 
продолжение?»

Не события. Намёк. Открытая дверь. Человек смотрит не в камеру, а чуть за кадр. За столом стоит ещё один стул. Телефон лежит экраном вниз, но вибрирует. Эти детали создают off-frame tension → desire vector → пользователь хочет нажать «исследовать».
