Архитектура: explore / context_shift / local_edit — где сходятся, где должны расходиться

Дата: 2026-05-17
Контекст: Денис только что выкатил wish-классификатор (InterpretWishAndGenerateJob) — пожелания пользователя автоматически делятся на local_edit vs context_shift. Параллельно есть explore (continuation без пожелания) — самая старая ветка. Все три ветки сейчас живут в одной воронке «новый кадр», и эта смешанность — часть причины, по которой explore «коллапсирует в вариацию».

1. Что есть сейчас (production)

Три точки входа — одна воронка

Действие пользователя UI кнопка Backend ветка Что отправляется в FAL
«Хочу сейчас ещё один кадр этой сцены» «Исследовать» base_source=previous_generation, без userComment photo_session prompt (ID=20) + scene_title + previous_variants → OpenRouter → FAL text2image с user-photo как anchor
«Сделай кофту синего цвета» «Регенерировать с комментарием» base_source=previous_generation, с userComment Wish classifier → local_edit → photo_session prompt + scope-guard → FAL image-edit с previous_image как base
«Я иду у горы Кайлас» «Регенерировать с комментарием» base_source=previous_generation, с userComment Wish classifier → context_shift → wish_scene prompt (ID=34) + selfie → FAL text-to-image с selfie как anchor

Где разделение уже работает

После работы Дениса 2026-05-17: - local_edit правильно отделён: image-edit режим + scope-guard «не меняй лицо, возраст, образ, фон, композицию, одежду — только то, что в пожелании». ✅ - context_shift правильно отделён: text-to-image + selfie face-lock + новый метапромпт wish_scene (ID=34, сейчас пустой, нужно наполнять).

Где смешано до сих пор

explore (continuation без пожелания) — самая давняя ветка, остался на том же photo_session prompt (ID=20), что и был. По логике он = «context_shift без пользовательского пожелания, с автоматическим continuation сигналом». Но архитектурно он живёт как раньше и не получил отдельного narrative-движка.

Это и есть структурная причина, почему explore генерирует вариации, а не следующий момент: его обслуживает прампт, написанный как «универсальный continuation», в котором смешаны и развитие момента, и расширение мира, и углубление эмоции, и параллельный угол — шесть равноценных режимов одновременно. Модель выбирает безопасный путь = декорация.

2. Нарративная роль каждого режима (зафиксировать)

Режим Кинематографический аналог Что меняет Что держит Когда триггерится
local_edit re-touch / colour correction только то, что назвал пользователь всё остальное (поза, локация, момент, костюм-минус-правка) wish + classifier=local_edit
explore next shot в той же сцене следующий микро-момент в пределах часа, новый ракурс, развитие действия локацию, день, костюм, эмоциональный регистр без wish, base=previous
context_shift cut to новой сцене локация, контекст, событие, иногда время дня идентичность, эмоциональный вектор, уровень жизни wish + classifier=context_shift
«sphere shift» (пока нет) cut to новой главе фильма новая сфера, новая жизненная тема, новые сцены идентичность, профиль первичный выбор сферы пользователем

Важно: explore сейчас претендует на роль «next shot в той же сцене», но фактически выдаёт что-то ближе к мини-context_shift («ещё одна сцена на ту же тему сферы»). Это первое, что нужно починить.

3. Карта сигналов — что каждый режим должен получать

Сейчас архитектура примерно симметрична: все три режима делят photo_session prompt (с небольшими модификациями для local_edit). Это неправильно — у них разные нарративные роли, значит разные сигналы.

Local edit

Получает: - previous image (для image-edit base) - wish text (что менять) - scope-guard суффикс (что не трогать)

Не должен получать: - profile_summary (избыточно для re-skin) - previous variants list (нет relevance) - continuation logic (нет смысла) - spatial/temporal logic (тоже)

Сейчас в gen 632 — получает ВСЁ это. photo_session prompt в полном объёме, плюс полный профиль одежды, плюс инструкции по continuation. Это шум, который потенциально может всё-таки «толкнуть» модель сменить позу или фон. Сейчас работает чисто только потому, что image-edit режим биасован против больших изменений.

Идеально — radical simplification: local_edit получает 200-словный промпт «edit X in this image, preserve everything else» + image. Это всё.

Context shift

Получает (после новой архитектуры Дениса): - selfie (identity anchor) - wish text - original scene description (для эмоциональной преемственности) - sphere_title + sphere_definition - profile_summary - wish_scene prompt (ID=34, пустой)

Не должен получать: - previous image (text-to-image, не image-edit) - previous_generated_variants (новая сцена — нерелевантно)

Это правильная архитектура. Осталось наполнить ID=34 — там должно быть НЕ photo_session, а другой, более компактный промт, заточенный под «свобода в новой локации, держим идентичность и эмоциональный вектор, не держим композицию и блокинг».

Из кинематографического ревью: главная проблема 633 (Кайлас) — постановка скопирована один-в-один с 631. Это значит, что метапромпт wish_scene должен явно разрешать менять блокинг, ракурс, дистанцию, выбирать camera grammar под локацию (Кайлас → environmental wide, не medium шага).

Explore

Сейчас получает (gen 634): - scene_title (зафиксирован) - scene_description - sphere_title + definition - profile_summary (полный) - onboarding_answers (полные, частично избыточно) - previously_generated_variants (3 предыдущих описания целиком) - photo_session prompt ID=20 (21149 символов с 10 секциями)

Должен получать (после правок): - scene_title + scene_open_loop + scene_position (narrative-designer’s пункт 5.1+5.2) - anchor_object (continuity prop) - spatial_zones (где мы внутри локации) - emotional_beat (текущий бит из 4-битовой структуры) - previously_generated_variants как «откуда мы пришли», не как «что не повторять» - compressed profile (200-300 символов, не 5К) - explore-specific prompt (новый, не photo_session ID=20)

Не должен получать: - onboarding_answers (избыточно при наличии profile_summary) - full sphere_definition (она уже отражена в scene_title) - 10 дублирующих секций continuity (Narrative Continuity Engine ≈ Story Momentum ≈ World Unfolding Logic — оставить одну)

4. Структурный пробел — отсутствие scene_state

Главное архитектурное упущение: у сцены нет state. Каждый explore генерируется как stateless вызов «вот сцена, вот предыдущие варианты, сделай следующий». Между explore-ами не сохраняется никакая прогрессия.

Сейчас: - iter 1: сгенерировали кадр в хабе - iter 2 (local edit): тот же кадр, цвет кофты - iter 3 (context shift): другая сцена (Кайлас) - iter 4 (explore): обратно в хабе, но в лаунже — этот переход никто не отслеживает

Должно быть так: - сцена 631 имеет state: {position: "midway", clock: 30min, open_loop: "встреча с инвестором", anchor: "кожаный баул olive", zones: ["coridor","lounge","exit"], current_zone: "coridor", emotional_beat: "движение"} - iter 4 (explore) читает этот state, продвигает clock на 20min, перемещает в lounge, продвигает emotional_beat к «ожидание / собранность», сохраняет anchor, держит open_loop неразрешённым. - Когда open_loop разрешается (например, на 4-м explore) — сцена закрылась, дальше идёт context shift в новую сцену.

Это persistent scene state на уровне data model — то, что narrative-designer назвал «scene clock + open loop в first scene». Это самая большая структурная правка, и она важнее всех изменений промптов.

5. Что менять в коде (по приоритетам)

Приоритет 1 — Persistent scene state (data model)

Добавить в GenerationRequest или Scene сущность поля: - scene_open_loop: string (что должно произойти; не показывается пользователю; держится скрытым) - scene_position: enum {start, middle, end} (где мы в сцене) - scene_clock: int (условные минуты от начала; +10-30 на каждый explore) - anchor_object: string (continuity prop, например “кожаный баул olive”) - spatial_zones: array<string> (карта пространства) - current_zone: string (где сейчас) - emotional_beat: enum {entry, recognition, contact, resonance, exit} (микро-arc)

first scene generator отдаёт эти поля наряду с описанием. explore generator читает их и продвигает.

Усилие: 1 миграция БД + правка first scene metaprompt (просит LLM вернуть JSON с этими полями) + правка explore metaprompt (использует их).

Эффект: базовый — explore перестанет быть stateless, начнёт двигаться по карте сцены.

Приоритет 2 — Разделить explore prompt от photo_session prompt

Сейчас explore использует photo_session ID=20 (21149 символов с 10 секциями). Создать отдельный prompt для explore (например ID=35) — компактный, заточенный под: - читает scene_state (новые поля выше) - использует previously_generated_variants как историю, не как тормоз - двигает scene_clock и emotional_beat - 1500-2500 символов вместо 21K

photo_session ID=20 пусть останется для context_shift / sphere-init scenes (другая роль, можно отдельно тюнить).

Усилие: написать новый prompt + одна точка-роутер в коде.

Эффект: explore перестанет получать противоречивые инструкции «продолжай / не повторяй / делай что угодно».

Приоритет 3 — Наполнить wish_scene prompt ID=34

Сейчас пустой. Денис ждёт нашего метапромпта для context_shift. Должен быть: - 1500-3000 символов - НЕ photo_session (другая роль) - держит identity + emotional_vector + lifestyle_level (не локацию, не блокинг) - разрешает смену camera grammar под локацию (Кайлас ≠ хаб) - не дублирует scope-guard правила local_edit - ожидает что код добавляет structured context block (Денис уже это делает)

Усилие: написать prompt ~2K символов.

Эффект: context_shift перестанет выдавать «green screen replacement» из идентичной постановки.

Приоритет 4 — Sphere arc (3-4 узловые сцены)

Сейчас сфера = 3 первые сцены, каждая существует параллельно, между ними нет логики «утро → день → закат». Перестроить структуру сферы: вместо 3 параллельных «углов» — 3-4 узловые точки одного дня жизни.

Усилие: изменение sphere metaprompts, миграция данных — это не одна неделя.

Эффект: сфера ощущается как «проживаемый день», а не «галерея кадров».

Приоритет 5 — Camera grammar diversity (operator-side)

Кинематографическое ревью показало, что 8/8 кадров — eye-level centered medium. Это собственно вообще не narrative проблема, это operator vocabulary. Промпты должны явно запрашивать разнообразие grammar: - 30% explore = wide environmental (герой 1/8 кадра) - 20% = close-up fragment (руки, объект, отражение) - 20% = OTS / POV (с плеча героя или его глазами) - 30% = medium (текущий дефолт)

Это можно встроить либо как тип бита (entry = wide, contact = medium, resonance = close-up), либо как явный параметр в explore prompt.

Усилие: добавление параметра + 5-10 строк в prompt.

Эффект: визуальный ритм появится автоматически.

6. Что НЕ делать архитектурно

Не объединять три режима обратно в один

Соблазн «упростить» воронку до одного universal-prompt — провалит свежее разделение Дениса и вернёт смешанность. Три режима должны оставаться архитектурно независимыми, делиться только базовыми сигналами (identity, profile).

Не отдавать выбор режима пользователю

Кнопка «explore / shift / edit» наружу = разрушит интуитивность. Классификация остаётся в backend (для wish — через LLM-классификатор, для explore — implicit «нет wish + есть previous»).

Не делать persistent state «прозрачным» для пользователя

scene_open_loop = "встреча с инвестором" — это внутренний скрытый state. Пользователь не должен его видеть, иначе ломается ощущение «жизни». Это движок, не interface.

Не вытаскивать scene_state из БД в UI

Соблазн показать «вы прошли 30% сцены». Не нужно. Это narrative tool для LLM, не геймификация для пользователя.

Не дублировать identity anchoring логику в трёх местах

Сейчас identity preservation описана и в photo_session (Identity Continuity Rules + Identity Anchor Continuity), и в новом wish_scene будет, и в local_edit scope-guard. Один шейред блок identity_lock на 300-500 символов, который импортируется во все три prompt-а. Без дублей.

8. Финальный анкер

Архитектурно три режима должны жить раздельно, но делиться: - общим identity anchor module - общим profile_summary (compressed) - общим scene_state (когда применимо)

И у каждого должна быть своя точка истины в виде отдельного prompt с понятной нарративной ролью: - local_edit = retouch (минимальный prompt) - explore = next shot в той же сцене (с scene_state) - context_shift = cut to новой сцене (с identity carry)

Когда эти роли разведены архитектурно и каждый prompt подаёт только нужные сигналы — путаница «explore = вариация» исчезает на уровне инфраструктуры, не на уровне ещё одной директивы в промпте.
